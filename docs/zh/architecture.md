# 架构与设计逻辑

[文档导航](README.md) · [English](../architecture.md) · [快速上手](getting-started.md)

GBClaw 面向的是会随着证据积累而改变方向的研究。研究者可能先比较一批晶界，发现其中一个响应异常，再围绕它提出新的物理问题。系统既要保证不同案例使用一致的计算方法，也要支持有针对性的后续分析，并保留新旧结果之间的联系。

本文解释这些需求如何影响架构设计，依据框架论文中的架构、记忆和讨论部分编写。各专题文档说明当前代码的具体实现；框架论文和相关晶界物理研究见[参考文献](../references.md)。

## 一个协调者，多个专职 agent

Orchestrator 是研究者的统一交流入口，负责理解请求、安排下一步工作，并把结果带回讨论。五类专职 agent 分别负责规划、晶体学、LAMMPS 模拟、分析和自定义代码。

![研究者、orchestrator、专职 agent、项目记忆与科研计算后端](../assets/paper-architecture.png)

*框架论文图 1。当前实现将研究记录保存在 SQLite 中，将科研输出保存在文件中。图中部分集成需要额外安装软件；planning agent 的网页搜索仍是扩展接口。*

这样划分是为了控制每个 agent 的任务范围和上下文大小。例如，结构 agent 需要晶体几何信息和相关已有结构，无须读取项目中的所有图表和聊天记录。每次委派因此会包含明确目标、已知约束和证据引用；worker 按需查询更多细节，最后返回状态、发现和输出引用。

执行顺序由科学依赖决定：分析弛豫结构之前，必须先得到该结构。不同晶界案例之间可以并行，但要受计算资源预算约束。委派决定“由谁完成”，资源准入决定“何时可以开始”。详见 [agent 运行时](agent-runtime.md)和[资源配置](configuration.md)。

## 计划保留研究者的判断

计划让较大研究任务中的假设和依赖在执行前就可以被检查。Planning agent 生成草案，研究者审阅或提出修改，明确批准后才激活。范围清晰的单项任务可以直接执行，无须每次新建计划。

执行开始后，计划记录进度并引用产生的 run。研究方向变化时，系统生成可审阅的修订，同时保留已完成工作。例如，批量筛选可以引出某个晶界的 NEB 研究，而不必覆盖原有筛选历史。

Planning agent 负责提出方法，科学工具负责产生结果，研究者负责判断结果是否回答了科学问题。这三类职责贯穿整个研究过程。[运行时文档](agent-runtime.md#delegate-tools)说明计划批准、修订和执行的具体流程。

## 标准工具与自定义代码各有用途

常规计算需要稳定的输入、检查和输出记录，才能在不同案例之间比较。Structure、LAMMPS 和 Analysis 工具提供这些可重复使用的工作流。模型选择工具并解释结果，工具负责数值过程和输出保存。

Coding agent 处理现有工作流没有覆盖的小型任务，例如读取特殊数据格式或制作自定义比较图。它接收选定的 artifact，在隔离的临时工作区中执行脚本，经过验证后发布选定输出。Python 环境从宿主维护的注册表中选择。可选的 `ase` 环境为 Atomic Simulation Environment 提供接入方式，需要先安装环境和软件包。

这种分工既保留探索空间，也避免每次计算都重新定义常用方法。如果某个脚本反复使用，维护者可以在检查物理假设、输入和数值行为后，将它整理为正式的领域工具。详见[科学工具](tools.md)、[自定义代码](coding-agent.md)和[扩展接口](extension-guide.md)。

## 记忆将研究概况与详细证据分开

近期对话、项目概况和轨迹文件解决的是不同问题。分开保存后，agent 可以用较小的上下文继续交流，同时保留查询详细证据的能力。

| 信息层 | 用途 | 示例 |
| --- | --- | --- |
| 领域知识 | 说明方法和工具规则。 | 合法的 NEB 设置需要哪些输入。 |
| Project summary | 帮助 agent 掌握整个研究的状态。 | 当前目标、重要发现、未解决问题和检索入口。 |
| 近期对话与 Session summary | 衔接当前讨论。 | 研究者刚提出，下一步要比较两个已经完成的案例。 |
| 持久研究记录 | 让主张和计算可以被检索。 | Run 的输入与状态、有来源的结论及输出引用。 |
| Artifact | 保存完整科研材料。 | 原子结构、数值数组、轨迹、日志和脚本。 |

**Run** 记录一次工作流执行，**fact** 记录有来源的主张或项目状态，**artifact** 是已登记的输出文件。稳定 ID 将它们连接起来。例如，一个应力下降结论应能追溯到对应的剪切 run、分析数据和相关原子结构。

Project summary 本来就不是完整记录。压缩时应优先保留当前目标、重要发现和待解决问题，减少较早完成工作的细节。旧版摘要仍保存在 SQLite 中，当前摘要通过归档 ID 和简短主题预览说明如何找回省略内容。完整计算记录和 artifact 不依赖摘要而存在。详见[项目记忆](project-memory.md)。

完整聊天和工具调用轨迹另行保存，供人类回看。从已完成的用户—助手交流中提取的主张保留对话来源，不会因为写入数据库就变成计算结果。工具结果、对话提取内容、agent 报告和工作流状态在检索和摘要中仍可区分。

## 项目比一次对话上下文存在得更久

项目是持久的研究工作区。浏览器刷新、服务重启或很久以后再回来，都不会因此清除其中的研究记录和 artifact。Thread 标识项目内某段对话的执行状态；时间间隔本身不要求新建 thread。重新进入同一项目时，可以继续它已有的 thread。

两类摘要分别支持这种连续性。**Project summary** 描述项目层面的持久研究状态；**Session summary** 帮助模型跟上当前 thread 的讨论，而不必重读完整历史。两者都不替代研究记录。对应代码边界是：`agents/middleware/` 管理对话上下文，`project_memory/snapshot/` 准备只读记忆快照，`project_memory/summary/` 管理 Project summary。

网页界面背后的 HTTP API 和终端 CLI，每一轮都经过 `interfaces/turn.py` 中的同一条流程：取得执行占用、准备会话、运行 orchestrator 流、保存这一轮交流，并启动回答完成后的记忆处理。两种入口只在输入解析和事件显示上不同。项目占用机制控制哪个前端拥有当前对话，防止重叠请求同时修改执行状态。可见回答结束后，后端可能仍在保存这一轮内容和更新记忆。界面会显示收尾状态，待执行占用释放后再允许下一次请求。详见 [API 与界面](api-and-ui.md)。

## 一项研究如何经过这些层

假设研究者想知道，为什么某个镍晶界比其他相关晶界更难发生滑移。

| 阶段 | 系统职责 | 研究者职责 |
| --- | --- | --- |
| 明确问题 | 找回相关已有工作，识别缺少的输入。 | 确定科学目标和约束。 |
| 制定计划 | 提出可比较的案例、计算、依赖关系和检查方法。 | 审阅假设、选择设置并批准计划。 |
| 执行计算 | 构造结构、运行计算，保存输入、状态和 artifact。 | 按需检查中间结果。 |
| 分析结果 | 比较响应，将数值变化与结构联系起来。 | 判断证据是否支持提出的解释。 |
| 调整方向 | 起草有针对性的后续工作，例如 NEB 计算。 | 决定下一步验证哪种解释。 |
| 稍后继续 | 恢复简明项目概况，再按需查询具体记录。 | 回到同一项目，提出下一个问题。 |

关键在于，后续问题能够找回一个结果的输入和证据。成功执行和正确的来源链接有助于复核；物理正确性仍取决于模型、参数、数值检查和科学解释。

## 便于扩展的代码边界

| 组件 | 负责内容 | 这样划分的原因 |
| --- | --- | --- |
| `core/` | 路径、配置、模型构建、执行会话与子进程监管，以及聊天流事件 schema。 | 共用基础设施不依赖任何领域或 agent 代码。 |
| `extensions/` | 领域声明注册表：worker、工具、记忆记录、capability 和宿主 hook。 | 新领域通过统一接口声明记录和策略。 |
| `project_workspace/` | 项目元数据、聊天归档、项目文件安全访问、执行占用和运行状态持久化。 | 持久工作区的管理与模型上下文分离。 |
| `project_memory/` | 记忆发布、artifact 清单、搜索、检索、快照和 Project summary。 | 所有领域的研究记录遵循同一套存储和来源规则。 |
| `planning/` | 计划草案、批准、修订、步骤进度和规划模式。 | 研究者的决定独立于任何 agent 保存和执行。 |
| `agents/` | 协调、worker 调用、对话上下文和事件报告。 | 新方法可以复用同一套执行生命周期。 |
| `domains/` 下的领域包 | 科学算法、输入、检查、领域输出解释，以及各领域的 worker、delegate、提示词和声明。 | 修改科学方法时，无须修改通用存储。 |
| `interfaces/` 与 `web/` | 共用的轮次流程、HTTP API、CLI、前端占用和研究界面。 | 界面可以改进，同时复用项目和执行契约。 |

各包按以下依赖顺序分层，`core` 位于最底层：`core` ← `extensions` ← `project_workspace` ← `project_memory` ← `planning` ← `agents` ← `domains` ← `interfaces`。Agent 层通过注册表中的 hook 字符串（`"module:attr"`）找到领域 worker、delegate factory、工具集和路由说明，因此新增领域不需要修改 agent 代码。orchestrator 自身的领域工具（`orchestrator_tools`）和 planner 对各领域步骤的规则（`planning_guidance`）同样由领域声明。

增加小型自定义计算，可以从 [coding 环境注册表](coding-agent.md#运行环境注册表)开始。增加反复使用的科学工具或新的专职 agent，使用[扩展开发指南](extension-guide.md)。[源码地图](src-code-map.md)列出了各项职责对应的位置。
